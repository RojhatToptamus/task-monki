# Discovery questions

Ask only when material product intent is unresolved. A clear brief needs no discovery ceremony.
Use your design judgment when a reasonable direction is available.

## Read the available context

Before you ask a question, inspect:

- the original brief and current request
- the current source and latest ready revision
- earlier user answers and conversation
- active references and local assets
- existing brand rules, components, tokens, and content

Do not ask for information that is already available.

## Decide whether a question is necessary

Ask only when different plausible answers would materially change a main design decision, such as:

- who will use the interface
- what task or outcome matters most
- which screens or flows are in scope
- which existing product, brand, or system the work must match
- whether an open request needs a specific format or level of fidelity

Start work without a question when the brief and context support a useful interpretation.
Infer repository facts and safe design details from available evidence.
For a vague product request, resolve materially different audiences or primary jobs before building.
Skip discovery for a focused refinement or exact recreation.
Make safe design choices yourself.
Do not ask about small labels, spacing, colors, or equivalent implementation details.

## Ask what is relevant now

Use the provider's structured question tool. Group independent questions that are relevant now.
Never ask a blocking question as ordinary transcript text.
If the tool is unavailable, proceed with a safe reversible assumption.
If material product intent cannot safely be inferred, report the blocker for a user follow-up.
Ask only questions whose answers can change the design.
Keep each question short and concrete.
Use two to four mutually exclusive choices with short descriptions when they make the answer easier.
Task Monki supplies custom input and a Decide for me action. Do not add those as choices.

Do not use a fixed question count.
Defer dependent questions until an earlier answer makes them relevant.
Ask a follow-up only if its answer still materially changes the product.
After you receive the answers, continue the same Design turn.
Do not ask follow-ups for minor details or repeat answered questions.

## Apply the answer

Use each answer in the implementation.
A later correction supersedes only the conflicting earlier decision; preserve unrelated requirements.
"Decide for me" delegates only that unresolved safe choice within the existing scope.
It does not replace other answers or authorize external side effects.
If one choice creates a clear user problem, explain the concern briefly and use the user's final decision.
Record only the assumptions that matter to the result.
Then select the matching Design skill and build.
